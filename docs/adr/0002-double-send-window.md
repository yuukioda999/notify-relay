# ADR-0002: 二重送信が起こりうる時間を最小にし、プロセスは1つで動かす

- ステータス: 承認
- 日付: 2026-11-05
- 決定者: 小田 裕貴
- 関連: specs/001-delivery(AC-R001-08・13・14)、ADR-0001

## コンテキスト

- SMTPサーバーがメールを受け付けた直後、その結果をDBに書く前にプロセスが強制終了すると、再起動後に同じ宛先へもう一度送る可能性がある。SMTPの仕組み上、これを完全に防ぐことはできない(spec の「送信」節)
- 一方で、通常の停止(SIGTERM)や、DBの一時的な障害で二重送信が起きてはいけない
- 並行して送るため(既定50)、同じ宛先を2つの送信処理が同時に扱わないようにする必要がある

## 検討した選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| **A** | **送信直前に `sending` と記録し、送信直後に結果を記録する。起動時に `sending` のまま残った宛先だけを `pending` に戻す。プロセスは1つ** | **二重送信が起こりうるのは「送信してから記録するまでの間に強制終了した」場合だけになる。仕組みが単純** |
| B | A に加え、宛先ごとに「どのプロセスが送信中か」と期限(リース)を持ち、複数のプロセスで動かす | 横に増やせるが、期限切れの判定や時計のずれの扱いが増える。今の規模(デモ環境は VPS 1台)では不要 |
| C | 送信前の記録をせず、結果だけを記録する | 強制終了のたびに、送信中だった宛先が未送信に見え、二重送信の可能性が大きくなる |

## 決定

案Aを採用する。

- 宛先は `FOR UPDATE SKIP LOCKED` で取り出し、同じトランザクションで `sending` にする。同じ宛先は1つの送信処理にしか渡らない
- 結果の記録では依頼の行を先にロックし、同じ依頼の宛先を1件ずつ記録する(最後の宛先を同時に記録したときのデッドロックを防ぐ)。記録に失敗したら数回やり直す
- 停止の合図を受けたら新しい送信を始めず、送信中のものの完了と記録を待つ。始めていない宛先は `pending` に戻す
- 起動時に `sending` のまま残った宛先を `pending` に戻す。これは強制終了のあとにだけ起こる
- このため notify-relay は1つのプロセスで動かす。2つ動かすと、片方の起動時に、もう片方が送信中の宛先を戻してしまう

## 結果

良くなること:

- 通常の停止、DBの一時的な障害、並行送信では二重送信が起きない。起こりうるのは強制終了(OOM、電源断など)のときだけで、その時間も送信1通ぶんに限られる

悪くなること・受け入れるコスト:

- 1プロセスで送れる量が上限になる。負荷試験(AC-R001-28)で目標の30万通/10分を満たすかを確かめる
- 強制終了の直後は、送信中だった宛先に二重送信が起こりうる。業務アプリ側は、同じお知らせのメールが2通届くことがありうる前提で文面を作る

## 見直す条件

- 負荷試験で1プロセスでは目標に届かない場合(案Bに移る)
- 冗長化のため、notify-relay を2台以上で動かす必要が出た場合
