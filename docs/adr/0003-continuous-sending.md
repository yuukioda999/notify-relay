# ADR-0003: 送信の処理を、まとまりごとに待たずに途切れなく続ける

- ステータス: 承認
- 日付: 2026-11-13
- 決定者: 小田 裕貴
- 関連: specs/001-delivery(AC-R001-08・13・14)、ADR-0002、team-ops の specs/008-load-test(負荷試験の直し方の段階2)

## コンテキスト

- 送信の処理は、送る時刻の来た宛先を 500件ずつ取り出し、同時に `SEND_CONCURRENCY` 通まで送り、500件がすべて終わってから次を取り出していた
- そのため、まとまりの中に遅い1通があると、ほかの送信の枠が空いていても次を取り出せない
- team-ops の負荷試験(30万通)では、relay 単体で同じ設定のまま 480秒と 776秒の揺れが出た。受け取り役の待ち時間を 0ms にしても速くならず、SMTP の待ち時間ではなく、この待ち方が上限を決めていると見ている

## 検討した選択肢

| 案 | 内容 |
|---|---|
| **A(採用)** | 送信の枠と同じ数の受け渡しの列を置き、列が半分空いたら次を取り出す。遅い1通はその枠だけを止め、ほかの枠は列から次を取って送り続ける |
| B | 一度に取り出す数を小さくする。まとまりごとに待つことは変わらず、取り出しの回数(DB への問い合わせ)が増える |
| C | 送信の枠ごとに、自分で1件ずつ取り出す。DB への問い合わせが1通ごとになる |

## 決定

- `Sender.Run` は、送信の枠(`SEND_CONCURRENCY`)と同じ数の受け渡しの列を持つ。列が半分以上空いたら、空いた数(最大 500件)を取り出して列に入れる。枠は列から1件ずつ取って送る
- 列の残り半分が枠を働かせ続けるので、取り出しの待ち時間で枠が空かない。取り出しは、半分がはけるたびに1回で済む
- 停止の合図のあとは新しい送信を始めない。送信中のものは終えて記録し、列に残っていた宛先は `pending` に戻す(AC-R001-14 は変わらない)
- 二重送信が起こりうる範囲(ADR-0002)は変わらない。取り出した宛先は今までどおり `sending` と記録してから送る
- `SendDue`(1回取り出して、すべて終えるまで待つ)は残す。`Run` からは使わない

## 結果

良くなること:

- 遅い1通が、ほかの送信を待たせない
- 送信の枠が、取り出しの合間にも空かない

悪くなること・受け入れるコスト:

- `sending` と記録された宛先が、送信の枠の数だけ多く列で待つことがある。強制終了したときは、今までどおり起動時に `pending` に戻る(AC-R001-13)
- 処理の流れが少し複雑になる。テストで、遅い1通があっても次が送られること、停止の合図での扱いを確かめる

## 見直す条件

- 1つのプロセスでは足りなくなり、複数のプロセスで送る必要が出た場合(ADR-0002 の案 B を見直す)
